# The pipeline, end to end

**What this document is.** A single map from "which library should I look at?" to "here is
a verified case", naming the script that does each step and the artifact it leaves behind.

It exists because the other two documents each cover part of it:

- [`README.md`](README.md) — what the project is looking for, the current findings, and
  the five screening rules that decide whether a library is worth mining at all.
- [`PIPELINE.md`](PIPELINE.md) — the stage mechanics of the **commit-search route**
  (`mine/bbc_e2e.py`), in detail.

Neither describes the **code-search route** end to end, and that is the route that
produced every jackson-core case in the dataset. This document covers both, and says which
to reach for.

> **Numbers live in [`output/reports/CENSUS.md`](output/reports/CENSUS.md)**, regenerated by
> `ledger/census.py`. Nothing here quotes a count, deliberately — a count in prose drifts.

---

## The shape of the whole thing

```
  PHASE 0   choose a break            is a case even POSSIBLE for this library?
     │
     ▼
  PHASE 1   find adaptations          which repos changed code because of it?
     │                                ROUTE A commit search   ROUTE B code search
     ▼
  PHASE 2   screen                    is the change a RECOVERY, or just a mention?
     │
     ▼
  PHASE 3   traversal                 did this client actually CROSS the boundary?
     │
     ▼
  PHASE 4   differential              pass → fail → pass, or it is not a case
     │
     ▼
  PHASE 5   record                    verified_cases/*.json, then census
```

Every phase can end the candidate's life, and an ending is a result: a measured zero is a
finding. The census distinguishes that from a stage that never ran (`--`).

---

## Phase 0 — Is a case even possible?

Cheap library-level checks, before any mining. The five rules and what each killed are in
[`README.md`](README.md#why-most-candidates-die--the-screening-rules); the scripts are:

| script | question it answers |
|---|---|
| `discover/mine_advisories.py` | what breaks exist? (pulls the OSV Maven feed) |
| `archive/mine_major_bumps.py` | same, for major releases of top libraries |
| `discover/rank_candidates.py` | does the boundary remove public API? (a compile break shadows the behavioural one) |
| `archive/screen_majors.py` | the same API check across curated major boundaries |
| `archive/boundary_dates.py` | is the boundary old enough that clients could cross it, or were they all born past it? |
| `discover/probe_population.py` | does *anyone* publicly commit this adaptation? measures the population, not the library |

Then one **manual** check no script does: read the `-sources.jar` diff and confirm the new
restriction is **active by default**. A restriction that ships opt-in, or a fix that
*removes* a restriction, cannot break anybody. This is the rule that most often decides.

Output: an entry in `specs/bump_breaks_catalog.json`, with the boundary **pinned
empirically** — old and new jars run side by side until the behaviour flips — before any
mining is spent on it.

## Phase 1 — Find adaptations

Two routes. They find different repositories, and the choice matters more than it looks.

### Route A — commit search  (`mine/bbc_e2e.py`)

```bash
python mine/bbc_e2e.py run <break_id>
```

Searches GitHub **commit messages and diffs**, on two axes: adaptation terms (the fix) and
bump terms (the upgrade), plus a forward scan after each bump so post-merge fixes are
reachable. Chains straight through classify and traversal, checkpointing each row.

Full mechanics — env vars, search modes, caps, the classifier's precision filters — are in
[`PIPELINE.md`](PIPELINE.md). Artifacts: `output/<break_id>_candidates.jsonl` and friends.

### Route B — code search  (the one that found the jackson cases)

Commit search is **recency-biased and cannot index some repositories at all**. On the
jackson break it returned most of its hits from 2026 — three years past the boundary,
where no crossing can exist. Code search asks a different question: *which files contain
this identifier today?* Then each file's history is walked to date it.

```bash
# 1. find files containing the adaptation API (cached to a hits JSON)
python discover/find_adaptations.py --via code-search \
    --identifier StreamReadConstraints --default-value 5000000 --out <hits>.json

# 2. date each repo: when was the call INTRODUCED?
python archive/date_hits.py \
    --hits output/_jackson_codesearch_hits.json \
    --identifier StreamReadConstraints \
    --out output/_jackson_dated.jsonl \
    --boundary-date 2023-04-22
```

`date_hits.py` bisects each file's history rather than walking it (the identifier is
present today and was introduced once, so "contains it" is monotonic — ~7 fetches instead
of up to 100).

**Two traps this script has already fallen into, both now fixed and both worth knowing:**

1. It used to date a repo by **one** file, chosen by shortest path. 47% of repos match more
   than one file, and path length says nothing about time — so a repo whose adaptation was
   old in one file but which later added the call to a shorter-named file got dated by the
   *later* file and dropped out of the window. It now dates **every** matching production
   file and takes the **earliest**. That single fix recovered datahub, trino, tika, nifi
   and besu from "born past the boundary". Regression test: `verify/test_date_hits.py`.
2. `--identifier` must be the **broadest** form of the API, not a specific setter.
   `setStreamReadConstraints` misses every client that goes through
   `new JsonFactoryBuilder().streamReadConstraints(...)` — including already-verified ones.
   Use the class name.

## Phase 2 — Screen: is it a recovery, or just a mention?

**The value the client chose is the whole game.** A project touching a limit API is doing
one of several quite different things, and only one of them is a case:

| verdict | what it means | is it a case? |
|---|---|---|
| `raise` | limit lifted (e.g. `Integer.MAX_VALUE`) — previous behaviour restored | **candidate** |
| `lower` | tightened further — security hardening, the opposite of a break response | no |
| `knob_at_default` | set to exactly the library's own default — config plumbing that changes nothing | no |
| `library_source` | the repo *is* the library — an API definition, not a client call | no |
| `no_call_in_diff` | the identifier is in the file but not in the dated commit's diff | no |
| `needs_reading` | the value can't be read from the diff | **a queue, not a bin** |

```bash
python archive/screen_dated.py --dated output/<break>_dated.jsonl --out <break>_screened.jsonl \
    --knob maxStringLength=5000000 --window-start 2023-04-22 --window-end <...> \
    --library-class StreamReadConstraints --group-id com.fasterxml.jackson.core
```

Three filters, cheapest first: **window** (an adaptation outside the crossing window can't
be a case however real it looks), **value** (the table above), **build** (Maven only —
that is what the differential drives).

`needs_reading` means the regex couldn't decide, not that the answer is no. arangodb sat in
that bucket and is a verified case: its values are reflective `Invocation` objects rather
than builder calls, which no regex could be expected to read.

Two other screens exist for questions the value screen doesn't ask:

| script | question |
|---|---|
| `screen/screen_compile_break.py` | is this behavioural, or does the client stop at javac? |
| `screen/screen_trigger.py` | does the client's data or usage ever REACH the changed path? |

## Phase 3 — Traversal: did this client actually cross the boundary?

**Calling the adaptation API proves nothing on its own.** Azure/azure-sdk-for-java added a
complete reflective `StreamReadConstraints` adaptation while pinned to jackson 2.13.5 —
because azure-core supports users who bring their own newer jackson. That is an adaptation
without a crossing, and it is not a case.

```bash
python traversal/find_crossing.py --repo <owner/name> --path pom.xml \
    --property auto --keyword jackson --boundary 2.15.0
```

Bisects a build file's history for the first commit at or past the boundary. **Three-valued,
and the values are not interchangeable:**

- **confirmed** — the version went from below to at/past the boundary in this file's history
- **genuine_negative** — never reaches it, or starts already past it (born beyond)
- **undecided** — the version is absent at the transition: managed by a parent POM or BOM,
  or the history is broken by a repo restructure. **An UNKNOWN, not a negative.**

That third value is load-bearing. ICIJ/datashare came back `undecided` because its module
had been split into its own repository and merged back; the real crossing was on the merge's
*second parent*. Had `undecided` been collapsed into negative, a verified case would have
been discarded.

Resolving undecideds, in escalating order:

| script | how it decides |
|---|---|
| `archive/extract_undecided.py` | pull the undecided rows out of a classify checkpoint |
| `archive/resolve_undecided.py` | ask `mvn dependency:tree` in the module that changed |
| `archive/closeout_traversal.py` | second pass — in a multi-module repo the module that changed is often not the one declaring the dependency |
| `traversal/resolve_version.py` | what does a client's build actually RESOLVE to? |
| `archive/retraverse.py` / `audit_traversal.py` | re-run over mined candidates / record the verdict into each case file |

**When the version arrives transitively, none of the bisects can see it.** benchto declares
no jackson version anywhere — it inherits airbase, which imports spring-boot-dependencies.
Its crossing was found by resolving both sides with `mvn dependency:list`, i.e. by asking
Maven rather than reading the POM. Trino was the same shape, and worse: the commit *titled*
"Update jackson to 2.15.1" merely added a property, while the real crossing was an earlier
`Update airbase to 138`. **A commit message naming the library is not the crossing.**

## Phase 4 — The differential

**The definition of a case.** Rebuild the client three times, moving exactly one thing at
each step:

```
1_baseline   parent code  + old library  ->  PASS
2_broken     parent code  + new library  ->  FAIL   (the break)
3_adapted    their fix    + new library  ->  PASS
```

There is no partial credit. A candidate either completes this chain or it is an
**exclusion with a reason** (`verified_cases/excluded/<reason>/`).

### Which harness to use

| path | when |
|---|---|
| `verify/02_verify_bbc.py` | the client's **own suite** can express the break. Runs per-test differentially, so pre-existing flaky failures are fine — they never enter the baseline-pass set. |
| `agent/` (see `specs/AGENT_DESIGN.md`) | the client broke without a test for it. Two LLM seams in `agent/seams.py`: `generate_test` and `diagnose_nontrip`. Everything around them is deterministic. |
| **a hand-written harness in `scratchpad/<lib>-<client>-harness/`** | what every jackson case actually used. See below. |

### The hand-written harness — the common shape

Each is a `run_state.sh` taking `<label> <sha> <version>`, plus a driver:

```bash
bash run_state.sh 1_baseline <parent-sha> 2.14.2
bash run_state.sh 2_broken   <parent-sha> 2.15.0
bash run_state.sh 3_adapted  <fix-sha>    2.15.0
```

Rules that every one of them follows, each learned from a failure:

- **Build with the project's own build**, and move the version through **the project's own
  property** (`-Djackson.version`, `-Dadb.jackson.version`, `-Djackson-bom.version` …).
  Never edit a build file.
- **Drive the client's real production entry point.** Only the oversized input and `main()`
  are ours. If the trigger must be authored, say so in the case file as a threat to validity.
- **Print where the library jar was loaded from**, so a state cannot silently run the wrong
  version. Better still, print the **setting actually in force** (read it back reflectively)
  — then each state proves it *is* the configuration it claims, independently of whether it
  threw.
- **`mvn clean` between states.** Incremental compilation reuses the previous state's
  `.class` files after a checkout. For shaded builds this is sharper: without `clean`,
  the previous state's shaded jar gets re-shaded into the new one — the one plausible route
  to two states silently sharing a library version.
- **Any skipped check must be skipped in EVERY state**, even where it only fails in one.
  Otherwise states were built under different rules and the one-variable property is gone.
- **Add a fourth state when the crossing was a multi-version jump.** If the client went
  2.13 → 2.17, run the identical parent code at the boundary version too, to show the
  failure appears *at* the boundary rather than somewhere in between.

Environment traps, all met in practice: JDK on `PATH` ≠ `JAVA_HOME` (Maven follows the
latter, bare `javac` the former); Windows `MAX_PATH` can make a repo impossible to check out
in full (trino — use sparse-checkout **exclusions**, because Maven refuses a root POM whose
listed modules are missing); airbase's checkstyle fails the build on CRLF, which a default
Windows clone introduces into every file.

## Phase 5 — Record

One JSON per case in `verified_cases/<library>/`, or `verified_cases/excluded/<reason>/`.
What a case file must carry, beyond the obvious:

- the **measured** three (or four) states, with the exact exception text
- `in_repo_version_transition` — the crossing commit, transition, date, elapsed, and
  `traversal_confirmed_by_pipeline` (**false** if a human established it — the automation
  should never get credit it didn't earn)
- `restores_previous_behaviour` — and *how*. This is where the interesting variation lives:
  full restoration, bounded raise, re-parameterisation, or a configuration surface that
  restores nothing by default
- `threats_to_validity` — authored trigger, counterfactual state, skipped checks, baseline
  that isn't the client's actual previous version. Write them down; they are what makes the
  rest credible.

Then regenerate the ledger:

```bash
python ledger/census.py > output/reports/CENSUS.md
```

## Which route should I use?

**Start with code search** (Route B) for a break whose adaptation has a distinctive API
name. It reaches repositories commit search cannot index, and dating by file history puts
the crossing window in view instead of the last two years of noise.

**Use commit search** (Route A) when the adaptation has no distinctive identifier — when
the only trace is a version bump and a behavioural fix with nothing greppable in the code.

**Neither replaces reading the commit.** Two of the jackson cases turned on a detail no
screen could see: in vespa and trino, the file the code search *hit* was not the file where
the break can be demonstrated — vespa's `JsonWriter` builds generators (a read constraint
there is never exercised), and trino's `JsonUtils.parseJson` was already safe via airlift.
The exercisable site was a sibling call site changed in the same commit.
